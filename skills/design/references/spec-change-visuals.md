# spec / change 시각 설명 계약

본문을 쓰기 전에 **독자가 그림으로 답할 질문 → 그림 종류 → 근거**를 정한다. 주요 구조·성공 경로·실패 경로가 연결된 문서는 그림이 설명의 뼈대다. 표는 목록 비교를, 코드는 근거를 맡는다.

## 독자의 질문에 맞는 그림

| 질문 | 표현 | 그림에서 읽을 수 있어야 하는 것 |
|---|---|---|
| 누가 무엇을 책임지는가? | 경계가 있는 구조도 | 사용자 입구, 우리 모듈, 외부 서비스, 저장 위치, 연결 관계 |
| 요청이 언제 어디로 이동하는가? | 레인 시퀀스 | 주체, 순서, 화살표의 실제 데이터, 저장/응답 시점 |
| 무엇이 바뀌어 문제가 해결됐나? | 같은 축의 before/after | 동일한 주체·배치, 달라진 연결과 데이터, 실패 지점과 수정 지점 |
| 실패하면 무엇이 남는가? | 분기·상태 전이 | 실패 조건, 이미 끝난 작업, 재시도 범위, 사용자에게 보이는 결과 |
| 사용자는 무엇을 보게 되는가? | 화면 상태 변화 | 전/중/후 상태, 사용자 동작, 실제 결과. 구현 없는 화면은 개념도로 표시 |

단계가 없는 이름표 모음, 두 칸에 prose를 넣은 before/after 카드, `A → B → C` 한 줄은 다중 모듈 흐름을 설명하는 그림을 대신하지 못한다. 화살표에 데이터·행동을 쓰고 저장/응답/실패를 구별한다. 표를 SVG 사각형으로 옮기는 것도 시각 설명이 아니다.

## 화면과 본문 연결

- 설명은 `사용자 상황 → 그림 → 짧은 해설 → 코드 근거` 순서로 읽힌다. 본문·그림의 이름과 단계 번호가 같아야 한다.
- 전체 구조를 보여준 뒤 같은 배치에서 현재 단계만 강조한다. before/after의 동일 모듈은 같은 위치·색을 유지한다. 노드마다 무작위 색을 붙이지 않는다.
- 주요 `.scene`에는 대응하는 `.vis[data-v]`와 `.inl.vis-inl` 그림을 모두 둔다. 데스크톱은 스크롤 연동, 모바일은 본문 그림으로 같은 정보를 제공한다. 모바일 SVG id는 접두사로 구별한다.
- 복잡한 그림은 개요와 상세로 나눈다. 실제 표시 크기에서 글자 14px 이상을 목표로 하고, 12px 아래는 금지다. 좁은 화면에서는 세로 배치, viewBox 폭은 칸 폭 이하, font-size 13 이상. 큰 viewBox를 줄여 글자를 읽을 수 없게 만들지 않는다.
- SVG의 title/설명, 범례, 짧은 캡션을 제공한다. 색만으로 변경·오류를 구별하지 않는다. 인터랙션은 단계 전환이나 비교에 도움이 될 때 사용하고, 조작하지 않아도 핵심을 볼 수 있게 한다.
- 템플릿 그림은 배치 예시다. 실제 근거에 따라 주체·연결·데이터·분기를 다시 그린다. 자료에 없는 이벤트나 저장 위치를 채워 넣지 않는다.

## 완료 판정

`astack check`는 구조 검사의 통과일 뿐, 시각 설명의 품질 인증이 아니다. 결과 HTML 자체에서 다음을 확인한다.

1. 본문을 가리고 그림만 보아도 주요 주체, 데이터 이동, 결과를 설명할 수 있는가?
2. change에서는 before의 실패 위치와 after의 수정 위치를 짚을 수 있는가? spec에서는 중요한 실패 분기가 보이는가?
3. 실제 그림이 존재하고 주요 장면에 연결되어 있는가? 자리표시·빈 stage·장식 아이콘으로 채워져 있지 않은가?
4. 허용된 렌더링 도구가 있으면 넓은/좁은 화면에서 잘림, 글자 크기, 스크롤 연동을 확인한다. 렌더링을 확인하지 못했다면 미검증이라고 밝힌다. 차단된 브라우저 경로를 우회하지 않는다.

단일 문구·상수 수정처럼 관계나 상태 변화가 없는 작업은 필요한 차이를 한 표로 충분히 설명할 수 있다. 이 경우 짧은 Task 결과로 작성한다. 사용자가 상세 코드리뷰를 요청했거나 여러 경로가 바뀐 경우에도 핵심 흐름은 그림 하나와 3줄 이내.
